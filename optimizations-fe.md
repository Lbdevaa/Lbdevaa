# Оптимизации фронтенда: рабочие правила

Выжимка из видео «31 оптимизация Frontend» (https://www.youtube.com/watch?v=v6j_bilDOKc), пересобранная в
короткий набор правил. Из 31 техники здесь те, что дают выигрыш в обычном SPA, — каждая с условием, когда её
применять, и способом, который работает с первого раза. Остальные — в конце, одной строкой: их полезно знать, но
повод для них появляется редко.

## Главное правило

**Сначала метрика, потом оптимизация.** Три полевые метрики (Core Web Vitals) показывают, что именно болит:

| Метрика | Что меряет | Хорошо | Что обычно помогает |
|---|---|---|---|
| LCP | когда показан главный контент | ≤ 2.5 с | доставка: кэш, сжатие, размер бандла, картинки, preload |
| INP | задержка отклика на клик / ввод | ≤ 200 мс | меньше работы в main thread: разбиение задач, лишние рендеры |
| CLS | прыжки вёрстки | ≤ 0.1 | размеры у картинок и плейсхолдеров |

Цикл: полевые данные (Sentry / PageSpeed Insights) → худшая метрика на худшей странице → трасса в DevTools
Performance → одна правка → снова метрика. Так оптимизация всегда попадает в то место, где она заметна пользователю.

## 1. Доставка — настраивается один раз, работает всегда

**1.1. Кэш: HTML — без кэша, ассеты с хэшем — навсегда.**
`index.html` отдаётся с `Cache-Control: no-cache` (или `no-store`), файлы с хэшем в имени (`index-a1b2c3.js`) — с
`public, max-age=31536000, immutable`. Хэш меняется вместе с содержимым, поэтому новый релиз подхватывается сразу, а
повторный визит не качает ни одного неизменившегося байта. Файлы без хэша в имени (`logo.svg`, `manifest.json`,
service worker) — короткий кэш.

**1.2. Сжатие текстовых ответов: brotli, запасной вариант gzip.**
HTML, JS, CSS, JSON, SVG сжимаются в 3–4 раза. Включается на сервере или CDN; проверка — заголовок
`Content-Encoding: br` в Network. (Это не то же, что минификация: минификатор удаляет пробелы при сборке, сжатие
кодирует повторы при передаче — нужны оба, и оба обычно уже есть.)

**1.3. CDN перед статикой.** Ассеты отдаются с ближайшего к пользователю узла. Вместе с правилом 1.1 это даёт
почти мгновенную загрузку при повторных визитах.

**1.4. Code splitting по маршрутам и тяжёлым виджетам.** Каждая страница и всё тяжёлое, что открывается по
действию (редактор, плеер, эмодзи, оплата), — через динамический `import()`. Загрузчик должен уметь повторить
импорт при сбое сети и пережить деплой, после которого старых чанков уже нет.

**1.5. Следить за стартовым бандлом.** Tree shaking бандлер делает сам; задача разработчика — не втащить тяжёлую
библиотеку в стартовый граф одним импортом. Раз в релиз смотреть, что попало в initial-чанки (bundle analyzer).

## 2. Загрузка данных и картинок

**2.1. Независимые запросы — параллельно.** Если `products` не зависят от `user`, они стартуют одновременно
(`Promise.all`, параллельные `useQuery`). Ожидание = самый долгий запрос, а не сумма.

**2.2. `loading="lazy"` — для картинок ниже первого экрана.** Для картинки первого экрана (hero, LCP-элемент) —
наоборот, обычная загрузка и `fetchpriority="high"`. У каждой картинки указаны `width`/`height` или `aspect-ratio`,
чтобы не было прыжков (CLS).

**2.3. Картинка по размеру места.** `srcset` + `sizes` с 2–3 вариантами ширины: телефону — 480px, десктопу —
1200px. Для пользовательских фото варианты обычно генерирует бэкенд или CDN ресайзом по параметру.

**2.4. `preload` — для одного-двух ресурсов, которые браузер иначе найдёт поздно.** Типичный случай — hero-картинка
из CSS или шрифт первого экрана. Каждый preload должен быть использован на этой же странице.

**2.5. Поиск по вводу — debounce + последний ответ побеждает.** Запрос через ~300 мс после паузы, а ответы старых
запросов отбрасываются (`AbortController` или ключ запроса в React Query — он делает это сам).

## 3. React

**3.1. State живёт там, где используется.** Состояние подсказки — внутри `Search`, а не в `App`: перерисовывается
только тот, кому это нужно. Из Redux / контекста каждый компонент читает узкий селектор, а не весь слайс.

**3.2. Контекст — по одной теме.** Часто меняющиеся данные (тема, онлайн-статус) — в отдельном контексте от редко
меняющихся (язык, пользователь).

**3.3. Мемоизация — компилятором.** С React Compiler `memo` / `useMemo` / `useCallback` расставляются
автоматически и всегда с правильными зависимостями. Без компилятора — `memo` на тяжёлых узлах (таблица, график,
длинный список), найденных в React Profiler, а не на каждой кнопке.

**3.4. Длинные списки — виртуализация.** Сотни строк и больше — через библиотеку виртуализации
(`react-virtuoso`, `@tanstack/react-virtual`): она уже решает строки разной высоты, бесконечную подгрузку и
восстановление скролла.

## 4. Браузер

**4.1. Анимации — через `transform` и `opacity`.** Сдвиг панели — `translateX`, а не `left`; появление — `opacity`,
а не `height`. Эти свойства анимирует композитор без пересчёта раскладки.

**4.2. Сначала все чтения геометрии, потом все записи.** В цикле не чередовать `offsetWidth` и `style.width`:
сначала собрать размеры, затем применить изменения — раскладка считается один раз.

**4.3. Каждая подписка с отпиской.** `addEventListener`, `setInterval`, `setTimeout`, сокеты, observer'ы — в
`useEffect` с cleanup, который снимает ровно то, что повесил. Глобальные синглтоны модуля — исключение, они живут
всё время работы приложения.

## 5. Тяжёлая работа в main thread

**5.1. Длинную задачу — порциями.** Обработка, которая идёт дольше 50 мс, делится на куски с уступкой управления
между ними (`await scheduler.yield()`, запасной вариант — `setTimeout(0)`), а в React — некритичное обновление
через `startTransition`. Клик пользователя обрабатывается между порциями.

**5.2. Сначала отклик, потом остальное.** В обработчике клика — сначала обновить то, что видно (открыть модалку,
подсветить кнопку), а аналитику, запись в storage и прочее — после отрисовки кадра
(`requestAnimationFrame(() => setTimeout(work))` или `scheduler.yield()`).

**5.3. Вычисления на сотни миллисекунд — в Web Worker.** Парсинг больших файлов, обработка изображений,
шифрование — в worker, обмен через `postMessage` (для больших бинарных данных — transferable `ArrayBuffer`).

## Знать, применять по поводу

| Техника | Повод |
|---|---|
| `content-visibility: auto` | длинная статичная страница (лендинг, статья) без виртуализации |
| `contain: layout paint` | изолированный виджет, который часто перерисовывается (график, плеер) |
| Critical CSS inline | серверный рендер / статический лендинг, где LCP упирается в CSS |
| Service Worker с кэшем | приложению нужен офлайн-режим (PWA) |
| Selective hydration | SSR со стримингом (Next.js, React Server Components) |
| OffscreenCanvas | анимации и визуализации на canvas с тысячами объектов |
| WebAssembly | готовая библиотека на C++/Rust (кодеки, обработка изображений) |
| TypedArray | миллионы чисел / пикселей в памяти |
| Стабильная форма объектов (V8) | горячий цикл в профиле, где движок помечает деоптимизацию |
| Event delegation | ванильный DOM; в React события и так делегированы на корень |
