# Гигиена зависимостей и безопасность сборки

Правила для npm-проекта: что попадает в дерево зависимостей, как его обновлять, как защитить CI, секреты и машину
разработчика. Универсальные, без привязки к конкретному репозиторию. Основной вариант — **npm 12** (вышел 08.07.2026);
отличия для npm 11 указаны в правилах. Про размер бандла — [optimizations.md](optimizations.md), раздел 9;
безопасность самого приложения (XSS, токены, заголовки, утечки) — [app-security.md](app-security.md).
Источники и как применять — [README.md](README.md).

## Как читать

- **обязательно** — для любого проекта; нарушение — находка аудита;
- **по ситуации** — только при условии из правила;
- **Найти:** — как обнаружить нарушение; *(авто)* — проверяет инструмент.

## Главное правило

**Зависимость — это чужой код, который выполняется на машине разработчика, в CI и у пользователя в браузере.**
Главная цель атак сегодня — машина разработчика и CI: install-скрипт пакета читает токены и публикует ими заражённые
версии (Shai-Hulud, 2025; axios, март 2026). Поэтому политика установки задаётся настройками, которые работают сами,
а не памятью разработчика; каждая новая зависимость проверяется до установки, каждая существующая — обновляется
регулярно и маленькими порциями.

## 1. Установка

**1.1. Lockfile в git, в CI — только `npm ci`.** *обязательно*
`npm ci` ставит ровно то, что записано в `package-lock.json`, и падает при расхождении с `package.json`;
`npm install` в CI может молча поставить другие версии. Изменения lock-файла в PR читаются как код, источники
пакетов проверяет `lockfile-lint` (2.2).
**Найти:** `npm install` в workflow-файлах и Dockerfile; `package-lock.json` в `.gitignore`.

**1.2. Версии Node и npm — в одном месте и одинаковые везде.** *обязательно*
`.nvmrc` + `engines` в `package.json`, та же версия в CI (`actions/setup-node` с `node-version-file: .nvmrc`, **во
всех job**) и в базовом Docker-образе. Версия npm важна отдельно: Node 26 поставляется с npm 11 — npm 12 ставится явно
(`npm i -g npm@12` в CI и Dockerfile или `packageManager` в `package.json` + corepack). Настройки из 1.3 на младшей
версии npm **молча игнорируются**.
**Найти:** `node-version` в каждой job, `FROM node:` в Dockerfile, `npm -v` в логе CI.

**1.3. Политика установки — в корневом `.npmrc` в git.** *обязательно*

```ini
# npm 12
min-release-age=7
strict-allow-scripts=true
@company:registry=https://npm.pkg.github.com

# npm 11 вместо strict-allow-scripts (install-скрипты там разрешены по умолчанию)
# ignore-scripts=true
# allow-git=none
```

В npm 12 install-скрипты зависимостей, git- и tarball-зависимости запрещены по умолчанию; файл добавляет задержку
(2.3), строгий режим скриптов (2.1) и привязку приватного scope (1.5). Токенов в этом файле нет (1.4). В монорепо с
workspaces — **только в корне**: `.npmrc` внутри папки workspace npm игнорирует (при `npm install` из корня — молча).
**Найти:** нет корневого `.npmrc` в git; `.npmrc` в папках workspace; `npm config ls -l` в CI.

**1.4. Токены реестра — не в репозитории и только на чтение.** *обязательно*
В git — `.npmrc.example` без токена; настоящий токен — в `~/.npmrc` разработчика и в секретах CI, в Docker-сборку —
как build secret, чтобы не остался в слое. Для установки — токен **только на чтение** с коротким сроком: granular-токен
npm read-only, для GitHub Packages — токен с одним правом `read:packages`, а не `gh auth token` со всеми правами
пользователя. Любой install-скрипт может прочитать `~/.npmrc`: токен с правом записи превращает заражённый пакет в
червя.
**Найти:** `_authToken` в файлах репозитория (*(авто)* secret scanning); права токена в настройках GitHub / npm;
инструкция онбординга, предлагающая `gh auth token`.

**1.5. Приватный scope привязан к своему реестру.** *по ситуации: есть внутренние пакеты*
Внутренние пакеты — только под своим scope (`@company/…`), в корневом `.npmrc` — `@company:registry=https://…` (без
токена). Иначе dependency confusion: npm находит в публичном реестре пакет с тем же именем и более высокой версией.
Имя scope занять и в публичном npm.
**Найти:** внутренние пакеты без scope; `resolved` приватного пакета в lock-файле указывает на `registry.npmjs.org`.

## 2. Что попадает в дерево

**2.1. Install-скрипты зависимостей — только одобренные.** *обязательно*
- **npm 12:** скрипты заблокированы по умолчанию. `npm install-scripts ls` — кто хочет их выполнить;
  `npm install-scripts approve <pkg>` записывает разрешение в `allowScripts` корневого `package.json` **с версией**
  (`"esbuild@0.25.0": true`) — после обновления пакета одобрить заново; `npm rebuild` выполняет одобренные;
  `deny` / `prune` — запретить и почистить. `strict-allow-scripts=true` (1.3) превращает неодобренный скрипт из
  предупреждения в ошибку установки.
- **npm 11:** `ignore-scripts=true` + allowlist через `@lavamoat/allow-scripts` (`allow-scripts auto` записывает
  найденные пакеты с запретом, разрешение — вручную; `allow-scripts` выполняет разрешённые). Собственные скрипты
  проекта (`npm run`, `npm test`) выполняются в обоих случаях.
Многим пакетам скрипт не нужен (esbuild ставит бинарник через optionalDependencies) — одобрять только то, без чего
пакет не работает.
**Найти:** *(авто)* установка в CI падает при `strict-allow-scripts`; `npm install-scripts ls`; пакеты с
`"hasInstallScript": true` в `package-lock.json`.

**2.2. Только из реестра.** *обязательно*
git-URL, tarball-URL, `file:` / `link:` обходят проверки реестра и `npm audit`, а git-репозиторий может принести свой
`.npmrc` и снова включить скрипты. npm 12 запрещает git и tarball-URL по умолчанию (`allow-git`, `allow-remote` =
`none`); npm 11 — `allow-git=none` (1.3). Подмену `resolved` в lock-файле ловит `lockfile-lint` в CI, **со всеми
используемыми реестрами**:
`npx lockfile-lint --path package-lock.json --type npm --allowed-hosts npm npm.pkg.github.com --validate-https`.
**Найти:** *(авто)* `lockfile-lint` (код 1 при чужом хосте или http); `git+` / `https://…tgz` / `file:` в
`package.json`.

**2.3. Свежий релиз — не сразу.** *обязательно*
Взломанные версии находят и снимают за часы или дни (axios — за 3 часа). `min-release-age` в `.npmrc` действует на
любой `npm install` (в npm 12 исключения — `min-release-age-exclude`). Dependabot читает этот `.npmrc` и берёт
больший из своего `cooldown` и `min-release-age`; его security-обновления идут без задержки. Срочный фикс моложе
срока — разовым `npm install <pkg>@<версия> --min-release-age=0` с причиной в PR: флаг снимает задержку для всего
запуска, поэтому после — дифф lock-файла. Без флага слишком свежая версия падает с `notarget … with a date before
<дата>` — это задержка, а не «версии не существует».
**Найти:** нет `min-release-age` в корневом `.npmrc`; нет `cooldown` в `dependabot.yml` (по умолчанию 3 дня).

**2.4. Новый пакет — с проверкой до установки.** *обязательно*
- существует и тот ли это пакет: `npm view <name>` — загрузки, репозиторий, история релизов; опечатка в имени
  (typosquatting);
- что внутри на самом деле: `npm pack <name> --dry-run` — сайт npmjs.org не показывает git- и URL-зависимости, а
  показанный код может расходиться с тарболом;
- поддерживается ли (последний релиз, issues), сколько тянет зависимостей, есть ли install-скрипты, опубликован ли
  с provenance;
- есть ли нативная замена — каждая зависимость увеличивает поверхность атаки и бандл (optimizations 9.2).
Одной командой: `npq install <name>` (возраст, typosquatting, скрипты, provenance; проверка CVE — только со входом в
Snyk) или `sfw npm install <name>` (Socket Firewall — блокирует пакеты, помеченные как вредоносные).
**Найти:** при ревью — новые строки в `dependencies` / `devDependencies` без обоснования в PR.

**2.5. AI-агент: пакеты — после проверки, API — по документации своей версии.** *обязательно*
Модели выдумывают правдоподобные имена пакетов, атакующие их регистрируют (slopsquatting): агент ставит пакет только
через проверку 2.4 или `npq` / `sfw`. Пример из README — отправная точка, а не готовый код (неякорный regex
`/example\.com/` пропускает `evil-example.com`, `Math.random()` вместо `crypto`). API библиотек агент сверяет с
документацией **той версии, что стоит в lock-файле** (бандл в `node_modules`, `llms.txt`, исходники по тегу), — данные
обучения отстают.
**Найти:** при ревью PR агента — новые зависимости и вызовы API, которых нет в установленной версии.

**2.6. `npx` — только установленное или с версией.** *обязательно*
`npx some-package` каждый раз качает последнюю версию без lock-файла, проверки хэша и задержки. В скриптах и CI —
пакет в `devDependencies` (`npx` берёт его из `node_modules`) или `npx pkg@1.2.3`. MCP-серверы для AI-агентов (доступ
к файлам и переменным окружения) — в отдельной папке с lock-файлом, запуск `npx --prefix <папка> --no --offline <bin>`:
не установленное не скачивается.
**Найти:** `npx <pkg>` без версии в `package.json`, workflow-файлах, `.mcp.json`, документации.

**2.7. Фантомные зависимости — видны.** *по ситуации: npm 12*
`install-strategy=linked` (стабилен в npm 12) раскладывает `node_modules` так, что импорт пакета, не объявленного в
`package.json`, падает сразу, а не работает случайно через чужую зависимость.
**Найти:** сборка / тесты с `--install-strategy=linked`.

## 3. Уязвимости

**3.1. `npm audit` в CI — по продовым зависимостям и с порогом.** *обязательно*
`npm audit --omit=dev --audit-level=high` — падает только на high / critical в том, что попадает в продукт. Полный
`npm audit` (с dev) — по расписанию: dev-пакеты выполняются в CI, где лежат секреты. `npm audit signatures` —
подписи и provenance установленного дерева.
**Найти:** *(авто)* шаг аудита в CI; его отсутствие — находка.

**3.2. Исправление — в отдельной ветке, сначала `--dry-run`, без `--force`.** *обязательно*
`npm audit fix --dry-run` → `npm audit fix` (в рамках semver). `--force` молча ставит мажорные версии — только
вручную, по одному пакету, как мажорное обновление (4.2). После — `npm ci`, линт, сборка, тесты, дифф lock-файла.
**Найти:** коммиты с `audit fix --force`; мажорные скачки версий в PR «security fix».

**3.3. Транзитивная уязвимость — через обновление родителя.** *обязательно*
Обновить пакет, который её тянет → если исправления нет, `overrides` с причиной в PR (почему и какая версия родителя
его снимет) → убрать override, когда родитель обновится. Нет исправления нигде — риск записывается (пакет, GHSA / CVE,
достижим ли уязвимый код) и пересматривается при следующем обновлении.
**Найти:** `overrides` в `package.json` без ссылки на причину; давние записи риска.

**3.4. Срок реакции зависит от критичности.** *обязательно*

| Severity | Срок |
|---|---|
| Critical | оценка в тот же день, исправление — сразу |
| High | до следующего релиза; блокирует деплой, если нет согласованного исключения |
| Moderate | в плановом цикле обновлений |
| Low | при случае, вместе с обновлением родителя |

**Найти:** открытые алерты Dependabot старше срока.

**3.5. `npm audit` видит не всё.** *обязательно*
- advisories фреймворка и сборщика (React, Next.js, Vite) — подпиской на их GitHub Security Advisories; база — GitHub
  Advisory Database / OSV;
- применимость — по тексту advisory, а не по интуиции: уязвимости React Server Components (декабрь 2025) не трогали
  чистое SPA, но трогали любое приложение на фреймворке с RSC, **даже без единой Server Function**;
- **после критической CVE ждать продолжения**: первые патчи RSC оказались неполными, за недели вышли ещё три CVE —
  следить за advisory и обновляться повторно; временные меры хостинга — не замена обновлению;
- компрометация пакета (вредоносная версия, а не уязвимость) — проверить lock-файл и его историю (`git log -S`) на
  заражённые версии; если ставилась — считать машину или раннер скомпрометированными и менять все доступные им секреты.
**Найти:** нет подписки на advisories используемого фреймворка; версия фреймворка ниже исправленной из последнего
advisory.

## 4. Обновления

**4.1. Регулярно, группами, ботом.** *обязательно*
Патчи и минорные — раз в неделю-две, одним PR на группу: Dependabot `groups` (`patterns`, `dependency-type`,
`update-types`), в монорепо — `directories` + `group-by: dependency-name`. Вслепую не обновлять: `npm update`,
`npx npm-check-updates -u` без ревью — антипаттерн; руками — `npx npm-check-updates --interactive`. В npm 12
одобрения скриптов привязаны к версии (2.1): PR, обновляющий пакет со скриптом, должен обновить и `allowScripts`.
**Найти:** нет `.github/dependabot.yml` (или Renovate); `npm outdated` — отставание на годы.

**4.2. Мажорная версия — отдельным PR.** *обязательно*
С чтением changelog / migration guide и прогоном тестов; не смешивать с другим, чтобы откат был одной операцией.
**Найти:** PR с мажорным обновлением и посторонними изменениями.

**4.3. `overrides` — с причиной и сроком.** *обязательно*
Каждый override документирован и пересматривается при обновлении родителя.
**Найти:** `overrides` без комментария в PR / README.

**4.4. Заброшенные пакеты — раз в квартал.** *обязательно*
Пакет без релизов годами — искать замену, пока в нём не нашли уязвимость, которую никто не исправит.
**Найти:** `npm view <pkg> time.modified` по прямым зависимостям.

## 5. Чистота дерева

**5.1. Без неиспользуемых зависимостей.** *обязательно*
**Найти:** *(авто)* `npx knip --dependencies` — заодно неиспользуемые файлы и экспорты.

**5.2. `dependencies` и `devDependencies` разделены честно.** *обязательно*
То, что нужно только для сборки, тестов и линта, — в `devDependencies`: от этого зависят точность
`npm audit --omit=dev` и размер продового образа.
**Найти:** линтеры, тестовые и сборочные пакеты в `dependencies`.

**5.3. Одна версия каждой библиотеки.** *обязательно*
**Найти:** `npm ls <пакет>`; исправление — `npm dedupe`.

**5.4. Лицензии совместимы с продуктом.** *обязательно*
Для закрытого продукта настораживают GPL / AGPL в коде, который попадает в бандл.
**Найти:** `npx license-checker-rseidelsohn --production --summary` (исходный `license-checker` не поддерживается).

**5.5. SBOM — когда о составе спрашивают снаружи.** *по ситуации: клиент, аудит, инцидент*
`npm sbom --sbom-format cyclonedx --omit dev > sbom.json` — встроено в npm.
**Найти:** запрос на SBOM, на который нечем ответить.

## 6. CI

**6.1. Actions — по lock-файлу или по SHA.** *обязательно*
Тег action можно перевесить на другой коммит. Лучше всего — lock-файл зависимостей workflow
(`.github/workflows/actions.lock`, генерирует `gh actions-lock`): фиксирует коммит каждого action, включая
транзитивные, и проверяет, что репозиторий под этим именем тот же. Без lock-файла —
`uses: actions/checkout@<sha> # v4.2.2`; тег — только для actions с бейджем «Verified creator». Reusable workflows
(`jobs.<id>.uses`) lock-файл не покрывает — их пинить по SHA. Обновления Actions — тем же ботом
(`package-ecosystem: github-actions`).
**Найти:** `uses: …@v<число>` / `@main` в workflow-файлах; *(авто)* OpenSSF Scorecard «Pinned-Dependencies».

**6.2. `GITHUB_TOKEN` по умолчанию — только чтение.** *обязательно*
Верхнеуровневый `permissions: contents: read` в каждом workflow, права сверх — точечно в job.
**Найти:** workflow без верхнеуровневого `permissions`; *(авто)* Scorecard «Token-Permissions».

**6.3. Данные события — не в `run:` напрямую.** *обязательно*
`${{ github.event.pull_request.title }}`, имя ветки, текст коммита в shell — внедрение команды. Только через `env:` и
`"$VAR"`.
**Найти:** `${{ github.event.` внутри `run:`; *(авто)* CodeQL для Actions.

**6.4. `pull_request_target` и `workflow_run` — без кода из PR.** *обязательно*
Эти триггеры работают с секретами и правом записи; checkout непроверенного кода в них — захват репозитория.
**Найти:** эти триггеры вместе с `actions/checkout` ссылки PR; *(авто)* Scorecard «Dangerous-Workflow».

**6.5. Изменения CI — через ревью.** *обязательно*
`CODEOWNERS` на `.github/workflows/`; защита основной ветки; Actions запрещено создавать и одобрять PR (настройка
репозитория / организации).
**Найти:** настройки ветки и Actions в репозитории; `CODEOWNERS` без правила на workflow.

**6.6. Секреты CI.** *обязательно*
Один секрет — одно значение (JSON целиком ломает маскирование в логах); производное значение (JWT из ключа, base64)
регистрировать как секрет (`::add-mask::`); секреты деплоя — в environment с обязательным ревьюером; ненужные —
удалять, остальные — ротировать.
**Найти:** список секретов репозитория — неиспользуемые и многострочные JSON; деплой-секреты вне environment.

**6.7. Self-hosted runner — изоляция job.** *по ситуации: свои раннеры*
Одноразовые / JIT-раннеры: следующая job не видит файлы и процессы предыдущей.
**Найти:** `runs-on:` с self-hosted меткой; конфигурация раннеров (переиспользуются ли между job).

**6.8. Бот видит приватные пакеты — с минимальным доступом.** *по ситуации: есть приватный scope*
Dependabot: `registries` с `type: npm-registry` и `scope: '@company'` — сам сгенерирует `.npmrc`; токен — в секретах
Dependabot, только на чтение.
**Найти:** Dependabot падает на приватных пакетах или не обновляет их.

**6.9. Проверка CI — автоматически.** *обязательно*
OpenSSF Scorecard action (пины, права токена, опасные триггеры) и CodeQL для workflow-файлов ловят 6.1–6.4 без
ручного ревью.
**Найти:** их нет в репозитории.

## 7. Машина разработчика

Правила о браузерной части приложения (публичные переменные сборки, CSP, Next.js) — в
[app-security.md](app-security.md).

**7.1. Машина разработчика — тоже периметр.** *обязательно*
В повседневной работе npm разлогинен, токенов с правом записи нет (1.4); чужой проект (тестовое задание, внешний
репозиторий) — в одноразовой VM без ключей и токенов, первая установка — с `--ignore-scripts`.
**Найти:** `npm whoami` в обычной сессии; права токенов в `~/.npmrc`.

## 8. Минимальный набор

**Файлы в репозитории:**

```ini
# .npmrc (корень, в git, без токенов; npm 12)
min-release-age=7
strict-allow-scripts=true
@company:registry=https://npm.pkg.github.com
```

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule: {interval: weekly}
    cooldown: {semver-major-days: 30, semver-minor-days: 7, semver-patch-days: 7}
    groups:
      minor-and-patch: {update-types: [minor, patch]}
  - package-ecosystem: github-actions
    directory: /
    schedule: {interval: weekly}
```

**Проверки:**

| Проверка | Команда / инструмент | Когда |
|---|---|---|
| Установка по lockfile | `npm ci` (npm 12, `strict-allow-scripts`) | каждый PR, каждая сборка |
| Источники пакетов | `npx lockfile-lint --type npm --allowed-hosts npm <приватный-хост> --validate-https` | каждый PR |
| Уязвимости в продовых зависимостях | `npm audit --omit=dev --audit-level=high` | каждый PR или ночью |
| Уязвимости во всём дереве | `npm audit --audit-level=high` | по расписанию |
| Подписи и provenance | `npm audit signatures` | каждый PR или ночью |
| Неиспользуемые зависимости | `npx knip --dependencies` | раз в неделю / релиз |
| Обновления и патчи безопасности | Dependabot / Renovate | автоматически |
| Версии Actions | `actions.lock` или SHA-пины | при каждом изменении workflow |
| Права токена, триггеры, пины | OpenSSF Scorecard, CodeQL | каждый PR в workflow |
| Новый пакет | `npq` / `sfw` / `npm view` + `npm pack --dry-run` | перед каждой установкой |
